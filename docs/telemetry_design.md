- 関係する文書: [タスクフロー設計](task_flow_design.md)、[実装計画](implementation_plan.md)（実装計画 0.3 で保留にしていたテレメトリー）

## 1. 目的

チャットで依頼して報告を受け取る形はそのままにして、その横に **エージェントが今していることを、ノードを生やしながら見せる窓** を置く。
見る人が一目で次の 4 つをわかるようにする。

1. 今、何をしているか（どのページを読んでいるか、LLM の答えを待っているか、利用者の答えを待っているか）
2. なぜそれをしているか（LLM が選んだのか、プログラムが変えたのか。変えた理由）
3. どこまで進んだか（網羅表の観点がどれだけ埋まったか、時間とページの枠がどれだけ残っているか）
4. 何を根拠にしたか（報告の事実が、どのページのどの引用から来たか）

### 今の Open WebUI で困っていること

| # | 問題 | 原因 |
|---|---|---|
| P-1 | ページを読んでいる間（例 C では 394 秒）、画面が止まって見える | 途中経過をノードが終わったときにしか流していない（`stream_mode="updates"`） |
| P-2 | 途中経過が文字の箇条書きだけで、流れ（どの判断がどの作業につながったか）が見えない | `<think>` の中に文字で流している |
| P-3 | 根拠の事実・引用・捨てた事実は実行記録（`runs/*.json`）を開かないと見えない | 画面に出す手段がない |
| P-4 | タイトル生成などの裏処理、モデル選択など、この用途では使わない機能が多い | 汎用のチャット画面のため |

## 2. 画面の構成

> 2026-11-20 の変更: 上の帯（今の作業・時間・ページ数）と、下の網羅表の帯・時間の帯はなくした。画面は「調査の一覧・チャット・ノードの窓」の 3 つだけにし、
> 網羅表はノードとして木に入れた（5 章）。今の作業はチャットの「調べています」の行に出す。下の図は当初の案。

```
┌───────────────────────────────────────────────────────────────────────────────┐
│ 上の帯: 今していること（1 文） │ 時間 212/900 秒 ▓▓▓░░ │ ページ 7/12 │ LLM ●● 2/2 │
├──────────────┬──────────────────────────────────────────────┬────────────────┤
│ チャット      │ 作業の流れ（ノードのグラフ）                     │ 詳細            │
│              │                                              │                │
│ 利用者: …     │  [依頼]→[判定]→[判断1]→[検索]→[判断2]→[読む]…  │ 選んだノードの   │
│              │                 │        ├ 結果 8 件          │ 中身（入力・出力・ │
│ 質問カード    │                 │        └ 同名の候補 2 件    │ 引用・点数の内訳・ │
│ （選択肢）    │                 └─[プログラムが変更]           │ 所要時間）        │
│              │                                              │                │
│ 報告（出典    ├──────────────────────────────────────────────┤                │
│ 番号から      │ 網羅表: 観点ごとの列に、事実のチップが溜まる      │                │
│ ノードに飛ぶ） │ 名称 ●●●● 確認済み │ 生態 ○ 未発見 │ …          │                │
├──────────────┴──────────────────────────────────────────────┴────────────────┤
│ 時間の帯: ノードごとの所要時間（ガントチャート）。LLM 待ち・Web 待ちを色分け            │
└───────────────────────────────────────────────────────────────────────────────┘
```

- **チャット（左）**: 依頼、質問への回答、報告を出す。報告の出典番号 [3] を押すと、グラフのそのページのノードを選ぶ
- **作業の流れ（中央）**: 主役。調査の進行に合わせてノードが生まれ、状態に合わせて形と色が変わる
- **網羅表（中央の下）**: 観点ごとの列。事実が確かめられるたびに、ページのノードから事実のチップが列へ飛んで溜まる
- **詳細（右）**: 選んだノードの中身をすべて出す（実行記録 `runs/*.json` の該当部分）
- **上の帯**: 今していることを 1 文で出す（例:「4 ページを並行して読んでいる（2/4 完了）。LLM の答えを待っている: ffpri.go.jp」）。止める条件の残り（時間・ページ・検索の回数）も出す
- **時間の帯（下）**: どこで時間を使ったか。LLM サーバーに接続できずに待った時間は別の色にする（調査の時間に数えないことと合わせる）
- スマートフォンの幅では、チャット → 上の帯 → 作業の流れ（縦に並べる）の順に積む。詳細は下から出る板にする

### 2.1 見た目の方針

- 白黒（白・黒・灰の濃淡だけ）。Open WebUI に近い、余白の多いシンプルな形にする。状態は色ではなく、形と動き（回る輪・点滅・斜線・取り消し線・✓・✕）で表す
- ノードには、そのページのサイトのアイコン（favicon）と、取ってきた画像のサムネイルを載せる。アイコンが取れないサイトは頭文字にする
- アイコンと画像は、サーバーが取得して保存したものを配る（`GET /api/assets/{key}`）。画面から外部のサイトに直接取りに行かない（取得の回数を減らし、利用者の情報を外部に出さないため）
- 利用条件で載せられない画像（「ALL RIGHTS RESERVED」など）は、サムネイルを出さず「許可が必要」と出す

## 3. ノードの種類

グラフのノードは LangGraph のノード（9 種類）より細かくする。**1 つのノード = 見る人が「1 つの作業」と思う単位**（設計書 7.1 の深掘りタスクの単位に合わせる）。

| 種類 | 生まれるとき | 形 | ノードの上に出す情報 | 子ノード |
|---|---|---|---|---|
| 依頼 | 依頼を受けたとき | 角丸の長方形（大） | 依頼文 | 判定 |
| 判定 | `check_feasibility` | 菱形 | 調べられる / 一部だけ / 調べられない、理由 | — |
| 判断 | `decide` のたび | 小さな円（巡回の背骨） | LLM が選んだ行動。プログラムが変えたら二重の輪と「変更」の印 | 次の作業のノード |
| 検索 | `search` | 横長の長方形 | 検索の言葉、種類（自由 / Tier 1 の site: / 観点 / 食い違い）、点数、結果の件数、応答しなかったエンジン | 結果の束、同名の候補 |
| 結果の束 | 検索の結果が返ったとき | 小さな点の集まり | 件数、対象の名前を含む件数、Tier の内訳（点の色） | — |
| 同名の候補 | Wikidata の候補が見つかったとき | チップの列 | 候補の名前と説明、sitelinks | — |
| 質問 | `ask_user` | 吹き出し | 質問文と選択肢。答えを待つ間は点滅 | 回答 |
| データベース | L3 を引いたとき | 円柱 | データベースの名前、記録の件数、失敗 | ページ（記録） |
| ページ | 読む順番が来たとき | 書類の形 | ドメイン、Tier（調整したら矢印付き）、段階（取得 → LLM → 照合）、事実の数（照合できた / 捨てた） | 事実、たどった参照 |
| 事実 | 引用を照合できたとき | 小さなチップ | 事実の短い文、観点の色 | — |
| 食い違い | `check_conflicts` で見つかったとき | 赤い稲妻の印 | 事柄、値の組 | — |
| 画像の候補 | `find_images` | サムネイル | 段階（L1〜L5）、Tier、取得 → VLM → 判定、確信度 | — |
| 報告 | `respond` | 角丸の長方形（大） | 書いている / 完了、出典の数 | — |

### エッジ（線）の種類

| 種類 | 線 | 意味 |
|---|---|---|
| 流れ | 実線（灰） | 判断 → 作業 → 次の判断 |
| 生成 | 細い実線 | 検索 → 結果の束、ページ → 事実 |
| 参照の追跡 | 点線＋矢印 | ページの出典欄からたどったページ（深さを数字で出す） |
| 転載 | 二重の点線 | ほぼ同じ文章のページどうし（独立した出典として数えない） |
| 根拠 | 観点の色の細い線 | 事実 → 網羅表の列 |
| 食い違い | 赤の破線 | 食い違う事実どうし |

## 4. 状態と動き

どのノードも同じ状態の型を持ち、**状態は形と色と動きの 3 つで同時に表す**（色だけに頼らない）。

| 状態 | 見た目 | 例 |
|---|---|---|
| 予定 | 薄い輪郭だけ | 読む順番待ちのページ |
| 実行中 | 輪郭が回る（進み具合がわかるときは円グラフで埋まる） | ページを取得している |
| LLM 待ち | 中で点が 3 つ脈打つ。経過秒数を出す | ページの本文から事実を抜き出している |
| 利用者待ち | 吹き出しがゆっくり点滅。チャットの入力欄も光る | 質問の答え |
| 完了 | 塗りつぶし。数字（事実 6 件など）を出す | — |
| 失敗 | 斜線と理由の短い文（HTTP 403 など） | 取得できなかったページ |
| 捨てた | 灰色、取り消し線 | 不採用の画像、照合できなかった事実 |
| プログラムが変更 | 二重の輪と「変更」の印。線で元の選択と新しい選択を並べる | LLM は「回答」→ プログラムが「ページを読む」に変更 |

- **「今」を追う**: 新しいノードが生まれたら、画面をそこへ動かす。利用者が自分でグラフを動かしたら追うのをやめ、「今に戻る」ボタンを出す
- **並行する作業**: ページの並行読み・画像の取得は、同じ列に縦に並べ、それぞれの段階を同時に動かす
- **事実が網羅表へ飛ぶ**: 照合できた事実のチップが、ページのノードから観点の列へ動いて溜まる。列の状態（未発見 → 出典不足 → 確認済み）が変わったら列の色を変える
- **時間の帯**: 上の帯の時間は、調査の時間（`guard.elapsed`）と上限 900 秒、報告のための残り 300 秒を目盛りで出す
- 動きは `prefers-reduced-motion` のときは止め、状態の変化だけを出す

## 5. グラフの並べ方

調査を **左から右へ伸びる木** にする。根が依頼、その子が判断（巡回）、判断の子が作業、作業の子がページ・画像の候補・データベースの記録。

```
[依頼]─┬─ 判定: 調べられる
       ├─ 判断 1: 検索 ──────── [検索] ─┬─ 同名の候補 2
       │                                ├─ 結果 8 件
       │                                └─ 概要 Wikipedia
       ├─ 判断 2: 回答 → 読む [変更] ─ [読む 1] ─┬─ データベース ─┬─ iNaturalist
       │                                         │                └─ GBIF
       │                                         ├─ ffpri.go.jp ✓ 事実 6
       │                                         └─ gov-online ✕ 403
       ├─ 判断 3: 回答 → 画像 [変更] ─ [画像] ─┬─ L2 写真 ✓
       │                                        └─ L3 許可が必要
       └─ …
```

- 縦の位置は木の整列（tidy tree）で決め、親は子の真ん中に置く。子が増えると親と下の枝が押し下げられる
- **滑らかに伸ばす**: 新しいノードは親の位置から生まれて、目標の位置まで動きながら現れる。並べ直しで動くノードも、目標の位置へ毎フレーム近づける（線もノードに付いて動く）
- 網羅表もノードにする: 依頼の子に「網羅表」（いちばん上に置く）、その子に観点のノード。ページで照合できた事実は、ページのノードから観点のノードへ飛んで溜まる。
  観点の状態は枠の形で表す（未発見 = 点線、出典不足 = 灰の面、確認済み = 黒の実線）
- **実るように生まれる**: 親から枝（線）が先に伸び、その先端の小さな実がノードの大きさまで、少し行き過ぎて戻るように膨らむ
- 自動では畳まない（最初からすべて展開）。作業のノードの「畳む ▾」で利用者が畳める
- **ノードの窓の拡大・縮小**: 木が広がると、全体が窓に収まるよう滑らかに縮小する（縮小しきっても収まらなければ、いちばん新しいノードのあたりを見せる）。
  ホイール・ピンチで拡大・縮小、ドラッグで移動できる。利用者が動かしたら自動をやめ、「全体」ボタンで自動に戻る
- 子ノード（ページ・画像の候補）は Tier の高い順に上から並べる（読む順番と同じ）

### 5.1 流れの図（2026-11-20 に追加。最初に出す表示）

木のほかに、エージェントの処理の流れそのもの（LangGraph のグラフと同じ形）をノードと線で描く表示を置き、窓の左上の「流れ / 木」で切り替える。

```
[依頼] → [判定] → [判断] ─┬→ [聞き返し] ─┐
            │             ├→ [検索] ─────┤（戻りの線で判断へ）
            ↓             ├→ [ページを読む] → [読んだページ] → [網羅表]
 [調べられないことの報告]  ├→ [画像] → [確かめた画像]
            │             ├→ [食い違い] ─┘
            └──────────→  └→ [報告] → [終わり]
```

- ノードの位置は決まっている。調査の間、今いるノードが光り（実行中・LLM 待ち・答え待ち）、作業が移るたびに線の上を点が流れる
- 線には通った回数（×3）を出し、太さも回数で変える。プログラムが LLM の選択を変えたときは、LLM が選んだ行き先への線を点線で一瞬出して消し、「変更 n」を線に残す
- 各ノードには、通った回数・かかった時間・最近の出来事（3 つ）を出す。押すと、すべての出来事を詳細に出す
- 「読んだページ」はページのアイコンを並べ、読んでいる段階（取得・LLM・完了・失敗）を形で出す。照合できた事実は網羅表の観点へ飛ぶ。アイコンを押すと、そのページの事実と引用を出す

## 6. イベント（画面に送る情報）

### 6.1 仕組み

- ノードの中から、作業の始まり・途中・終わりを **イベント** として送る。LangGraph の custom stream（`langgraph.config.get_stream_writer()`、`stream_mode=["updates", "custom"]`）を使う（2026-11-19 に langgraph 1.2.20 で動くことを確認）
- `read_pages` などは `ThreadPoolExecutor` の中でページを並行して読む。スレッドの中では `get_stream_writer()` が使えない（実行の文脈が引き継がれない）ので、ノードの最初に取り出した writer を、スレッドで動く関数に引数で渡す
- 送る処理は 1 か所（`agent/telemetry.py` の `Emitter`）にまとめ、ノードの処理と混ぜない。Emitter がないとき（テスト・CLI）は何もしない
- イベントは画面に送ると同時に `runs/<実行の ID>.events.jsonl` に 1 行ずつ書く。後から同じ画面で **再生** できる（デバッグ・レビュー・研究の発表に使う）

### 6.2 イベントの形

```json
{"run": "20261119-184837", "seq": 42, "t": 61.3, "type": "node.update",
 "id": "page:ffpri.go.jp/snap/2015/6-kamoshika.html", "parent": "read:2", "kind": "page",
 "status": "llm", "label": "ffpri.go.jp", "data": {"tier": 1, "stage": "抜き出し", "llm_started": 58.1}}
```

| 項目 | 内容 |
|---|---|
| `run` / `seq` / `t` | 実行の ID、通し番号（抜けの検出）、調査の開始からの秒数 |
| `type` | `node.start`、`node.update`、`node.end`、`edge`、`status`（上の帯）、`chat`（チャットに出す文） |
| `id` / `parent` / `kind` | ノードの ID（同じページは同じ ID）、親ノード、種類（3 章の表） |
| `status` | 4 章の状態（`planned` / `running` / `llm` / `waiting_user` / `done` / `failed` / `dropped` / `overridden`） |
| `data` | 種類ごとの中身（下の表）。詳細の欄にそのまま出す |

### 6.3 どこで何を送るか

| 送る場所（今のコード） | イベント | data の中身 |
|---|---|---|
| `check_feasibility` | 判定の start / end | 判定、理由、調べられない部分 |
| `decide`（`check_decision` の後） | 判断の end | LLM の選択と理由、プログラムの変更（`guard`）、query_plan の点数と内訳、他の候補 |
| `search` | 検索の start、結果の束・候補の end、検索の end | 言葉、種類、結果（題名・URL・Tier・対象の名前を含むか）、応答しなかったエンジン、やり直したか、拾った表記ゆれ |
| `_lookup_databases` | データベースの start / end | 名前、記録、失敗 |
| `_read_one` | ページの start → update（取得した / LLM に渡した / 照合した）→ end | URL、Tier と調整の理由、本文の長さ、事実（照合できた / 捨てた理由）、見分ける特徴、別名、転載の元 |
| `read_pages` の終わり | 網羅表の status | 観点ごとの事実の数・独立した出典の数・状態 |
| `check_conflicts` | 食い違いの end と edge | 事柄、事実の組 |
| `find_images` / `_check_image` | 候補の start → update（取得 / VLM）→ end | 段階、Tier、大きさ、VLM の判定（文脈・見た目・刻印）、確信度、不採用の理由 |
| `ask_user` | 質問の start（`waiting_user`）/ end | 質問文、選択肢、回答 |
| `respond` | 報告の start / end、chat | 報告の本文 |
| `LLM._create` | LLM の呼び出しの start / end（ノードの `llm` 状態に使う） | どのノードの呼び出しか、待ち時間、トークン数、接続できなかったか |
| `http.get` | 外部サービスの待ち（任意） | ホスト、やり直し、429 |

## 7. サーバーの API

今の OpenAI 互換の API（`/v1/chat/completions`）は残す（Open WebUI や他のツールからも使えるように）。新しい画面用に次を足す。

| API | 内容 |
|---|---|
| `POST /api/runs` | 依頼を送って調査を始める。実行の ID を返す |
| `GET /api/runs/{id}/events` | イベントの流れ（Server-Sent Events）。`Last-Event-ID` で途中から受け直せる（画面を開き直しても続きから見える） |
| `POST /api/runs/{id}/answer` | 質問への回答。調査を続きから再開する |
| `GET /api/runs` | これまでの調査の一覧（依頼・日時・時間・結果の要約） |
| `GET /api/runs/{id}` | 1 つの調査の最終状態と報告 |
| `GET /api/favicon?host=` | サイトのアイコン（サーバーが取得して `runs/.assets/` に保存したもの。IP アドレスや内部の名前には取りに行かない） |
| `GET /api/image?run=&src=` | その調査のイベントに出てきた画像の縮小版。利用に許可が必要な画像は配らない |

- 実装では、`GET /api/runs/{id}` と `events.jsonl` の取得は作らず、イベントの流れ（SSE）で記録をすべて送る（終わった調査は送り終えたら閉じる）

- 会話の見分けは、今の「それまでの利用者のメッセージ」ではなく実行の ID で行う（Open WebUI に合わせた工夫が要らなくなる）
- 調査はサーバーの中のスレッドで動かし、画面との接続が切れても続ける（今は接続が切れると止まって見える）

## 8. 技術の選択

| 部分 | 案 | 理由 |
|---|---|---|
| 画面 | ビルドの要らない素の JavaScript・HTML・CSS（`src/research_agent/ui/`）。FastAPI が `/ui/` で静的ファイルとして配る | 試作で、木の整列と滑らかな動きは素の JavaScript で十分に作れることを確かめた。Node.js のビルドを Python のリポジトリと Docker に足さずに済む（当初の案は React + React Flow） |
| グラフ | ノードは HTML の要素、線は SVG。位置は自前で計算する | ノードの中にアイコン・サムネイル・進み具合を自由に置ける |
| 並べ方 | 5 章の木の整列（tidy tree）を自前で書き、目標の位置へ毎フレーム近づける | 並べ直しで動くノードも、線と一緒に滑らかに動く |
| チャットの文 | 報告の Markdown（見出し・箇条書き・太字・画像・URL・出典番号）を、文字を無害化してから自前で描く | 外部のライブラリを読み込まない |
| 通信 | Server-Sent Events | 一方向で十分。再接続が標準である |
| 保存 | 今の `runs/` に `*.events.jsonl` を足す | 新しいデータベースを入れない |

- 利用者は当面、研究室の数人。ログインは API キー（今の `AGENT_API_KEY`）だけにし、Open WebUI のアカウント機能は持ち込まない
- Docker の構成は `agent` が画面も配る形にし、`open-webui` は移行が終わったら外す

## 9. Open WebUI から移すもの・移さないもの

| 機能 | 扱い |
|---|---|
| 依頼の入力・報告の表示（Markdown・画像） | 移す |
| 会話の履歴 | 移す（調査の一覧として。7 章の `GET /api/runs`） |
| 質問への回答 | 移す（選択肢はボタンにする） |
| 途中経過 | 置き換える（作業の流れの窓） |
| タイトル・タグ・続きの質問の自動生成 | 移さない（LLM の時間を使うだけ） |
| モデルの選択・ユーザー管理・プロンプト集 | 移さない |

## 10. 実装の段階

| 段階 | 内容 | 完了の条件 |
|---|---|---|
| T0 イベント（実装済み） | `agent/telemetry.py`（Emitter・Recorder）、6.3 の送る場所、`runs/*.events.jsonl` | CLI で実行すると jsonl ができ、ノードの start と end が対になっている（`tests/test_telemetry.py`） |
| T1 再生の画面（実装済み） | jsonl を読み込んで、作業の流れ・網羅表・詳細を再生する。速さ（8×・30×・すぐ）と、ある時刻で止める指定（`?at=秒`） | 2026-11-20 のニホンカモシカの記録で、完了の状態と 110 秒時点の状態を確認。例 B・例 C は未確認 |
| T2 生の画面（実装済み） | 7 章の API（`runs.py`）と SSE。チャットから依頼・回答・報告まで | 画面の API から依頼 → 報告まで動くことを確認。質問 → 回答の流れは偽物のグラフでのテストだけ（`tests/test_runs.py`） |
| T3 根拠をたどる | 報告の出典番号・事実から、ページのノード・引用へ飛ぶ。捨てた事実・不採用の画像も見られる | 報告のすべての事実から引用までたどれる |
| T4 置き換え | Docker から open-webui を外す。研究室のメンバーに使ってもらう | 実装計画フェーズ 7 の合格条件（メンバー 1〜2 人の利用）を、この画面で満たす |

- T1 を先にするのは、画面の作りを調査の実行と切り離して何度でも試せるため（LLM の待ち時間なしに見た目を直せる）
- 実装で見つかったこと: LangGraph の writer は呼ばれたときに実行の文脈（contextvars）を読むので、スレッドに writer を渡すだけでは届かない。Emitter を作るときに文脈を写し取り、送るたびにその写しの中で呼ぶ
- T0 だけでも、実行記録が時間の順に読めるようになり、今のデバッグが楽になる
