# テレメトリー画面の機能強化案（WebUI とエージェントの分離・モデルの切り替え）

- 作成: 2026-11-21
- 状態: X1（分離）を実装中（2026-11-21。ゲートウェイ・契約の 0・1 段・調査エージェントとチャットのサービス）。X2 以降は案
- 関係する文書: [テレメトリー画面の設計](telemetry_design.md)、[タスクフロー設計](task_flow_design.md)、[実装計画](implementation_plan.md)
- 比べた Open WebUI: 0.12.3（このリポジトリの Docker で動いているもの。サーバーの機能の入り口 `routers/` の一覧で確認）

## 1. 目的と前提

今のテレメトリー画面は「1 つの調査を始めて、作業の流れを見て、報告を読む」ことはできる。この案では、次の前提で作りを決める。

| # | 前提 | 今の作りで困ること |
|---|---|---|
| P-1 | エージェントは将来、**複雑な依頼**（比較・複数の対象・何段階もたどる調査）に対応する | 状態に持てる対象が 1 つだけ。画面も 1 つの調査 = 1 つの流れの図の前提 |
| P-2 | **複数の依頼**を同時に流す（まとめて依頼する、待ち行列で順に流す） | 調査はそれぞれ別のスレッドで動き、LLM サーバー（同時 4 件の共有）を取り合う仕組みがない |
| P-3 | **WebUI とエージェントを分ける**。別のエージェントへの差し替えや、エージェントを足すことが簡単にできる | 画面（`ui/app.js`）はエージェントのノード名（`read_pages` など）とイベントの中身を直接知っている。サーバーも 1 つのプロセスに画面・API・エージェントが同居している |
| P-4 | **モデルを切り替えられる**（研究室の LLM のほかに別のモデルも使う、役割ごとに使い分ける） | LLM は `.env` の 1 つだけで、すべての処理が同じモデルを使う |
| P-5 | Open WebUI の便利な機能（履歴・評価・設定・通知など）を、調査に合う形で取り入れる | 一覧と再生しかない |
| P-6 | **汎用にする**。調査エージェント専用の考え方（出典・事実・網羅表・Tier）を土台に入れず、普通のチャットのモデルや、出典を扱わないエージェントも同じ土台に載る | 画面も API も、調査エージェントの考え方を前提にしている |

## 2. 今できること

| 分類 | できること |
|---|---|
| 調査 | 依頼する、質問に答える、一時停止・再開する、最近の依頼から選ぶ |
| 見る | 流れの図・木で作業を見る、ノードの詳細（引用・判定・理由）、拡大・移動、記録の再生 |
| 報告 | Markdown の報告、出典番号からページへ飛ぶ、画像（ライセンス付き） |
| 一覧 | 調査の一覧（新しい順、状態付き） |
| API | `/api/runs`（開始・一覧・回答・一時停止・再開・イベント）、`/api/favicon`、`/api/image`、`/api/status`、OpenAI 互換の `/v1/chat/completions` |

## 3. 全体の構成: WebUI とエージェントを分ける

```
┌─────────────── WebUI（webui サービス） ───────────────┐
│ 画面（ui/）        ゲートウェイ（gateway/）                 │
│  チャット・一覧     ・利用者・認証・共有                     │
│  流れの図・木       ・調査の記録（RunStore: SQLite + jsonl）  │
│  分析・設定         ・調査の待ち行列（どのエージェントに渡すか） │
│                    ・イベントを画面へ配る（SSE）             │
│                    ・モデルの一覧と接続の状態                │
└──────────────▲──────────────────────────────────────┘
               │ エージェントの契約（4 章）: HTTP + SSE
     ┌─────────┼─────────────┬──────────────────┐
┌────┴────┐ ┌──┴────────────┐ ┌─────────────────┐
│ 調査     │ │ 複数対象の調査 │ │ 将来のエージェント │   … エージェントのサービス（agent-*）
│ エージェント│ │ （計画 → 分担）│ │ （論文要約など）   │
└────┬────┘ └──────┬────────┘ └────────┬────────┘
     └──────────── モデルの窓口（6 章）────────────┘
                   研究室の LLM ・ 他の OpenAI 互換のモデル
```

- **WebUI** は、エージェントの中身（LangGraph のノード名・状態）を知らない。知っているのは「エージェントの契約」（4 章）だけ
- **エージェント** は、画面の都合（色・並べ方・利用者）を知らない。契約どおりにイベントを出し、入力を受け取るだけ
- **ゲートウェイ** が両者をつなぐ。どのエージェントを使うか、記録の保存、利用者の権限、イベントの配信（画面を開き直しても続きから見られる）をまとめて受け持つ
- Docker では `webui` と `agent-research` を別のサービスにする。エージェントを足すときは、サービスを足してゲートウェイの設定（`config/agents.toml`）に 1 行足す
- **入口も差し替えられるようにする**。ゲートウェイの前に、使う側ごとの変換の部品（入口アダプター）を並べる。どれも同じ契約の上で動く

| 入口 | 内容 |
|---|---|
| テレメトリー画面 | ゲートウェイの API をそのまま使う |
| OpenAI 互換（`/v1/chat/completions`） | Open WebUI など。途中経過は文に、質問は応答の文にする（今の作り） |
| CLI | `scripts/agent.py` を、ゲートウェイの API を呼ぶ形にする |
| 将来の入口 | Slack・研究室のスクリプトなど。変換の部品を 1 つ足す |

### 3.1 今のコードとの対応

| 今 | 分けた後 |
|---|---|
| `server.py`（API・画面・エージェントの起動） | `gateway/`（WebUI 側の API・記録・待ち行列）と `agents/research/server.py`（契約を話すエージェント） |
| `runs.py`（RunManager） | ゲートウェイの「待ち行列と記録」と、エージェント側の「調査の実行」に分ける |
| `agent/telemetry.py`（イベント） | エージェント共通の部品（`agentkit/events.py`）。どのエージェントも同じ形でイベントを出す |
| `llm.py`（1 つの LLM） | モデルの窓口（`agentkit/models.py`。6 章） |
| `ui/app.js`（1,146 行） | 部品に分けた画面（8.1） |

## 4. エージェントの契約（Agent Protocol v1）

WebUI とエージェントは、次の API とイベントだけでつなぐ。別の言語・別の仕組み（LangGraph 以外）のエージェントでも、これを話せば差し替えられる。

### 4.0 契約の 3 つの段

契約は 3 つの段に分ける。どこまで対応するかは、エージェントが名乗り（4.2）の `levels` と `extensions` で示す。
WebUI は、名乗られた段の機能だけを出す（対応していない機能の欄やボタンは出さない）。

| 段 | 内容 | 画面でできること | 載るエージェントの例 |
|---|---|---|---|
| **0 段（必須）** | 依頼を受ける、文を返す（流しながらでよい）、状態の一行、終わる・失敗する | チャット・履歴・共有・書き出し（文）・通知・モデルの選択 | 普通のチャットのモデル（変換の部品を通して載せる）、簡単な要約のエージェント。Open WebUI と同じ範囲 |
| **1 段（任意）** | 作業（task）と段階（step）、質問・途中の入力・制御（一時停止・止める）、成果物（artifact）、設定の形（settings_schema）、処理の形（graph） | 作業の図・流れの図（一般的な並べ方）・時間の帯・設定の欄・質問への回答・一時停止 | 段階のある処理をするエージェント全般 |
| **2 段（拡張）** | 分野ごとの考え方。名前と版を付けて宣言する（例: `research/v1`） | 拡張ごとの画面の部品（例: 網羅表・出典のプレビュー・ページと画像の詳細） | 調査エージェント（`research/v1`）、将来の論文要約（`papers/v1` など） |

- **土台（ゲートウェイと共通の画面）は、0 段と 1 段だけを知っている**。2 段の拡張の中身は知らない
- 拡張は「イベントの種類」「成果物の種類」「画面の部品」を組で持つ。拡張の定義は `extensions/<name>/`（イベントと成果物の形の定義・画面の部品）に置く
- **汎用性の合格の条件**: 0 段の普通のチャットと、`research/v1` の調査エージェントの 2 つが、同じゲートウェイ・同じ画面に載る（9 章 X1）
- 汎用にしすぎない。あらゆるエージェントに合わせて共通の部分を薄くするのではなく、共通は 0・1 段に絞り、残りは拡張にする

### 4.1 API（エージェントが出す）

| API | 内容 |
|---|---|
| `GET /agent/v1/manifest` | エージェントの名乗り（4.2）。WebUI はこれを見て、設定の画面・流れの図・使える操作を組み立てる |
| `POST /agent/v1/runs` | 依頼を受ける。`{input: {text, files[], targets[]}, settings, models}` → `{run_id}` |
| `GET /agent/v1/runs/{id}/events` | イベントの流れ（SSE。`Last-Event-ID` で続きから） |
| `POST /agent/v1/runs/{id}/input` | 調査の途中の入力。`{kind: "answer" \| "steer" \| "feedback", ...}`（質問への答え、途中の指示、評価） |
| `POST /agent/v1/runs/{id}/control` | `{action: "pause" \| "resume" \| "cancel"}` |
| `GET /agent/v1/runs/{id}/result` | 結果（報告・事実・出典・画像・成果物）。決まった形（4.4） |
| `GET /agent/v1/health` | 動いているか、使えるモデルにつながるか |

- イベントの流れは、終わったら `event: end`、答え待ちになったら `event: rest` を送って閉じる（答えを待つ間は何時間にもなりうるので、つなぎっぱなしにしない）。ゲートウェイは答えを送った後につなぎ直す

### 4.2 エージェントの名乗り（manifest）

```json
{
  "id": "research", "name": "調査エージェント", "version": "1.4.0", "protocol": "1",
  "levels": [0, 1],
  "extensions": ["research/v1"],
  "capabilities": ["questions", "pause", "cancel", "steer", "files", "tasks"],
  "settings_schema": { "type": "object", "properties": {
      "max_seconds": {"type": "integer", "title": "時間の上限（秒）", "default": 900},
      "max_pages":   {"type": "integer", "title": "読むページの数", "default": 12},
      "images":      {"type": "boolean", "title": "画像も探す", "default": true},
      "databases":   {"type": "array", "title": "分野別データベース", "items": {"enum": ["ORCID", "iNaturalist", "..."]}}}},
  "presets": {"quick": {"max_seconds": 300, "max_pages": 6}, "thorough": {"max_seconds": 1800, "max_pages": 24}},
  "model_roles": [
      {"role": "decide",  "title": "判断",         "needs": ["json_schema"]},
      {"role": "extract", "title": "ページの読み取り", "needs": ["json_schema"]},
      {"role": "vision",  "title": "画像の確認",     "needs": ["json_schema", "vision"]},
      {"role": "report",  "title": "報告",         "needs": []}],
  "graph": {"nodes": [{"id": "decide", "label": "判断", "kind": "hub"}, {"id": "read_pages", "label": "ページを読む", "kind": "work"}],
            "edges": [["decide", "read_pages"], ["read_pages", "decide"]]},
  "events": {"version": "1", "types": ["step.start", "page.done", "..."]}
}
```

- **設定の画面は `settings_schema`（JSON Schema）から自動で作る**。エージェントが設定を足しても、WebUI は直さなくてよい
- **流れの図は `graph` から作る**。共通の画面は、ノードと線を左から右への層に並べる一般的な並べ方で描く（ノードの種類は `step`・`data`・`terminal` だけを知っている）。
  「判断を中心に作業が並ぶ」今の並べ方は調査エージェントの形に合わせたものなので、`research/v1` の画面の部品にする
- **使える操作は `capabilities` で出し分ける**（`steer` がないエージェントには途中の指示の欄を出さない）

### 4.3 イベントの形

```json
{"v": 1, "seq": 42, "t": 61.3, "run_id": "…", "task_id": "t2", "parent_task_id": "t0",
 "type": "page.done", "data": {"url": "…", "final_url": "…", "facts": [ … ]}}
```

- 今のイベント（`step.start`・`page.done` など）は、`data` に入れてそのまま使う
- **`task_id` で、どの作業（分担）のイベントかを示す**（5 章）
- イベントは段に合わせて分ける

| 段 | イベント |
|---|---|
| 0 段 | `run.start`・`run.end`（`report`）・`run.error`・`run.cancelled`・`message.delta`（文の続き）・`status`（状態の一行） |
| 1 段 | `task.created`・`task.start`・`task.end`・`step.start`・`step.end`・`question`・`answer`・`run.waiting`（答え待ちになった）・`run.paused`・`run.resumed`・`artifact` |
| 2 段（`research/v1`） | `search.*`・`page.*`・`image.*`・`databases`・`aspects`・`coverage`・`conflicts`・`source` |

- 拡張のイベントは `type` に拡張の名前を付けて送る（例: `research/v1:page.done`）。今のイベント名（`page.done` など）は、`research/v1` の中の名前としてそのまま使う
- 共通の画面は 0・1 段のイベントを必ず描く。拡張のイベントは、その拡張の画面の部品があれば描き、なければ詳細の欄に中身を出すだけにする
- 知らない種類・新しい版のイベントでも、WebUI は止まらない（古い記録の再生も続けられる）

### 4.4 結果の形

共通の結果は「報告」と「成果物の一覧」だけにする。分野ごとの中身は、拡張の成果物として入れる。

| 項目 | 段 | 内容 |
|---|---|---|
| `report` | 0 段 | Markdown の報告（普通のチャットなら応答の文） |
| `artifacts[]` | 1 段 | `{id, kind, title, media_type, data}`。比較表・年表など（Markdown・CSV・JSON）。`kind` に拡張の名前を付けられる |

`research/v1` の成果物（今の調査エージェントの結果）:

| `kind` | 内容 |
|---|---|
| `research/v1:facts` | `{id, text, quote, source_id, aspect, task_id}` の一覧。報告の文から根拠へたどる（C-2）のに使う |
| `research/v1:sources` | `{id, url, final_url, title, tier}` の一覧 |
| `research/v1:images` | `{url, source_id, level, license}` の一覧 |
| `research/v1:coverage` | 網羅表（観点ごとの事実の数と状態） |

- 書き出し（A-5）・評価（C-3）・比べる（C-4）は、共通の部分（報告・成果物）に対して作り、拡張があれば拡張の部品が詳しく扱う
  （例: 評価は 0 段なら報告全体に、`research/v1` なら事実・画像・出典ごとに付けられる）

## 5. 複雑な依頼と、複数の依頼

### 5.1 1 つの依頼を分担する（作業 = task）

複雑な依頼は、エージェントが**計画 → 分担 → まとめ**に分ける。作業（task）は 1 段の共通の機能なので、調査以外のエージェントでも同じ作業の図で見せられる。

```
依頼「A 先生と B 先生の研究を比べて、共同研究の可能性を整理して」
  └ 計画（task t0）
      ├ 調査: A 先生（t1）   … 今の調査エージェントと同じ流れ
      ├ 調査: B 先生（t2）
      └ まとめ: 比較と整理（t3。t1・t2 が終わってから）
```

- イベント `task.created {task_id, parent, title, kind, depends_on[]}`、`task.start`、`task.end` を共通のイベントにする
- 各作業の中のイベント（`page.done` など）には `task_id` を付ける
- 画面では、**作業の図**（作業どうしの依存関係。小さな有向グラフ）を上に出し、作業を選ぶとその作業の流れの図・木を出す
- 成果物は作業ごとに分けて持ち、まとめの作業がそれらを参照する。`research/v1` では、網羅表・出典・画像を作業ごとに持ち、出典番号は依頼全体で通し番号にする
- 今の調査エージェントは「作業が 1 つの依頼」として、そのまま契約に乗る（`task_id` を付けないイベントは、依頼全体の作業とみなす）

### 5.2 複数の依頼を流す

| 項目 | 内容 |
|---|---|
| まとめて依頼 | 一覧（例: 研究室の教員 10 人）を貼り付ける・CSV を渡すと、1 件ずつ調査にして 1 つのグループにまとめる |
| 待ち行列 | ゲートウェイが調査を待ち行列に入れ、同時に動かす数を決める（設定: エージェントごとの同時実行数） |
| 優先度 | 対話中の調査（利用者が画面を見ている）を、まとめて流す調査より先にする |
| モデルの取り合い | モデルごとに同時に送る数の上限を持つ（研究室の LLM は共有で 4。今は 1 つの調査の中でだけ 2 に制限している）。上限はモデルの窓口（6 章）が調査をまたいで守る |
| 進み具合 | グループの画面に、各調査の状態・時間・網羅表の埋まり具合を並べる。終わったものから報告を開ける |
| 中断と再開 | サーバーを立ち上げ直しても、待ち行列と途中の調査を続けられるようにする（チェックポイントを SQLite に置く。今はメモリ上） |

## 6. モデルの切り替え

### 6.1 モデルの一覧（`config/models.toml`）

```toml
[[models]]
id = "lab-qwen"                       # 画面に出す名前は title
title = "研究室 qwen3.8-27b"
base_url_env = "VL_BASE_URL"          # 接続先と鍵は .env から読む（リポジトリに書かない）
api_key_env = "VL_API_KEY"
model = "qwen3.8-27b"
capabilities = ["json_schema", "vision"]
max_concurrency = 2                   # このモデルに同時に送る数（調査をまたいで守る）
context_tokens = 32768

[[models]]
id = "other-openai-compatible"
title = "別の OpenAI 互換のモデル"
base_url_env = "OTHER_BASE_URL"
api_key_env = "OTHER_API_KEY"
model = "…"
capabilities = ["json_schema"]
max_concurrency = 4

[roles]                               # 役割ごとの既定のモデル
decide = "lab-qwen"
extract = "lab-qwen"
vision = "lab-qwen"
report = "lab-qwen"
```

### 6.2 決まりごと

- エージェントは「どのモデルか」ではなく「**どの役割か**」でモデルを頼む（`models.for_role("extract")`）。役割と必要な能力は、名乗り（4.2）の `model_roles` で出す
- 依頼ごとに、役割ごとのモデルを選び直せる（`POST /agent/v1/runs` の `models`）。選べないモデル（例: 画像を読めないモデルを `vision` に）は、ゲートウェイが受け付ける前に断る
- 画面では、入力欄のモデル名を選択の欄にする。ふだんは「全部まとめて 1 つ」を選び、詳しい設定で役割ごとに選べる
- モデルごとに接続の状態（今の `/api/status` を広げる）と、使った回数・時間・待ち時間を記録する。比較実験（フェーズ 8）で、モデルごとの成果を並べられる
- やり直し・待ち時間の数え方（レビュー 10）は、モデルの窓口 1 か所で行う
- モデルを足すのは設定ファイルに 1 項目足すだけ。OpenAI 互換でないモデルは、窓口に変換の部品（アダプター）を足す

## 7. Open WebUI の機能との比べ

| Open WebUI の機能（routers） | 調査エージェントでの扱い | 案 |
|---|---|---|
| chats（履歴・名前・ピン・アーカイブ・共有・書き出し）、folders、search | **取り入れる**。調査の記録は研究の資料になる | A |
| tasks（タイトル・タグ・続きの質問の自動生成） | **変えて取り入れる**。LLM を使わず、対象の名前・種類から付ける | A |
| 応答の作り直し・メッセージの編集・止める | **変えて取り入れる**。報告だけ作り直す、依頼を直して調べ直す、調査を止める | B |
| evaluations（応答の評価・比較） | **変えて取り入れる**。事実・画像・出典ごとの評価。フェーズ 8 と Tier の見直しに使う | C |
| 引用の表示 | **強化する**。引用の一節・Tier・本文の該当箇所まで見せる | C |
| チャットごとの設定 | **取り入れる**。エージェントの `settings_schema` から作る（4.2） | D |
| **models（モデルの選択・複数モデル）** | **取り入れる**。役割ごとのモデル選択と、モデルを替えた比較（6 章） | D・6 章 |
| knowledge・files・retrieval | **取り入れる**。手元の PDF・資料を出典として読ませる | E |
| memories | **変えて取り入れる**。確かめた事実と対象を、次の調査で使い直す | E |
| analytics | **取り入れる**。調査・モデル・作業ごとの時間・失敗・成果 | F |
| notifications | **取り入れる**。調査の終わり・質問・接続の切断を知らせる | F |
| users・groups・auths・mfa・scim | **一部だけ**。研究室の数人の利用者と権限 | G |
| functions・pipelines・tools・skills | **考え方を取り入れる**。エージェントの差し替え（4 章）と差し込み口（8 章） | 4・8 章 |
| automations・calendar | **後で**。決まった時刻に同じ調査を流す | 10 章 |
| audio、images（生成）、terminals、channels、notes | **取り入れない**（今の用途に要らない）。prompts は依頼のテンプレートとして D に含める | — |

### 8.1 画面を部品に分け、差し込めるようにする

```
ui/
  core/api.js        … ゲートウェイの API・SSE
  core/events.js     … イベントの受け取りと描き手の登録（registerRenderer）
  core/camera.js     … 拡大・移動
  core/schema-form.js… JSON Schema から設定の欄を作る
  views/tasks.js     … 作業の図（5.1。1 段）
  views/flow.js      … 流れの図（manifest の graph を一般的な並べ方で。1 段）
  views/tree.js      … 木（1 段）
  panels/chat.js、panels/details.js、panels/analytics.js、panels/queue.js（0 段）
  extensions/research-v1/*.js … research/v1 の部品: 判断を中心にした流れの図の並べ方、網羅表、
                                ページ・画像・出典の描き方と詳細、出典のプレビュー
```

| 差し込み口 | 内容 |
|---|---|
| `registerRenderer(type, fn)` | イベントの種類ごとの描き方。拡張のイベントは、その拡張の部品（`extensions/<name>/`）が登録する |
| `registerExtension(name, {renderers, nodeKinds, panels, layouts})` | 拡張の部品をまとめて登録する。名乗りの `extensions` にある拡張だけを読み込む |
| `registerNodeKind(kind, {draw, details})` | ノードの種類ごとの見た目と詳細の欄 |
| `registerAction(where, {label, run})` | 報告・ノード・調査に付ける操作（書き出し・評価・共有） |
| `registerPanel(id, component)` | 分析・待ち行列・比べるなどの画面 |

- ビルドは要らない（ES モジュールをブラウザがそのまま読む）。拡張の部品はゲートウェイが配り、画面は名乗りの `extensions` を見て必要なものだけ読み込む

### 8.2 エージェントの中の差し込み口（調査エージェント）

| 差し込み口 | 呼ばれるとき | 例 |
|---|---|---|
| `before_search(query)` | 検索の前 | 研究室のサイトを必ず site: で足す |
| `after_page(page, facts)` | ページを読んだ後 | 研究室の書式の資料から事実を取り出す |
| `source_tier(url)` | Tier を決めるとき | 学内の資料の Tier を上げる |
| `before_report(state)` | 報告を作る前 | 決まった書式（研究ノートの形）にする |
| `databases` | 分野別データベースを引くとき | 新しいデータベースを足す（今の `config/databases.toml` を広げる） |

- 差し込みは `plugins/` に置き、`config/plugins.toml` で有効にする。失敗はその差し込みだけの失敗として記録し、調査は続ける

### 8.3 記録の置き場（ゲートウェイ）

- `RunStore`（保存・一覧・検索・評価・グループ・待ち行列）を、まず SQLite で作る。イベントは jsonl にも書き続け、再生と持ち出しに使う
- 記録には、エージェントの id と版、使ったモデル（役割ごと）、設定を必ず残す（あとで比べるため）

## 9. 進め方

| 段階 | 内容 | 主な項目 | 完了の条件 |
|---|---|---|---|
| X1 分離 | エージェントの契約（4 章。0・1 段と `research/v1`）、ゲートウェイ、今の調査エージェントを契約に乗せる、0 段のチャットのエージェント（OpenAI 互換のモデルを包む部品）、Docker を `webui` と `agent-research` に分ける | 3・4 章、8.3 | 今の機能がそのまま動く（今のテストと、記録の再生が同じ見た目）。**0 段のチャットと調査エージェントの 2 つが、同じゲートウェイ・同じ画面に載る**。偽物のエージェント（テスト用）に差し替えても画面が動く |
| X2 モデル | モデルの窓口と一覧、役割ごとの選択、モデルごとの同時実行の上限 | 6 章、D-3 | 設定ファイルにモデルを足すと画面で選べ、役割ごとに別のモデルで 1 つの調査を流せる |
| X3 画面の部品化 | 画面を部品に分ける。manifest から設定の欄と流れの図を作る。今の調査専用の画面（判断を中心にした流れの図・網羅表・ページと画像）を `research/v1` の拡張の部品として作り直す | 8.1、D-1、D-2 | エージェントにノード・設定を足しても、画面を直さずに出る。拡張を持たないエージェントでは、網羅表などの調査専用の欄が出ない |
| X4 日々使う | 記録の管理、止める・作り直し、出典のプレビュー、通知 | A-1〜A-5、B-1、B-4、C-1、F-2 | 研究室のメンバーが Open WebUI を使わずに 1 週間使える（設計 T4） |
| X5 複数の依頼 | 待ち行列、まとめて依頼、優先度、待ち行列の画面、チェックポイントの永続化 | 5.2、F-3 | 10 件をまとめて依頼し、LLM の同時実行の上限を守って全部終わる。途中でサーバーを立ち上げ直しても続く |
| X6 複雑な依頼 | 作業（task）のイベント、作業の図、計画 → 分担 → まとめのエージェント | 5.1、D-4 | 「A と B を比べて」で 2 つの調査とまとめが流れ、出典が通し番号になる |
| X7 根拠と評価 | 文から根拠へ、評価、比べる、分析 | C-2〜C-4、F-1 | フェーズ 8 の比較実験（モデル違いを含む）をこの画面だけで行える |
| X8 関わる・資料 | 途中の指示、採否の直し、続けて調べる、資料を渡す、差し込み口 | B-2、B-3、B-5、E-1、8.2 | 調査の途中で観点を足すと網羅表と報告に入る。PDF を渡して出典として引用できる |

- X1〜X3 は見た目がほとんど変わらない作業だが、後のすべての段階の土台になるので先にやる
- 汎用にするための手間: 契約が 3 段になるので最初に作る量が少し増える。また X3 で、今の調査の画面を拡張の部品として一度作り直す
- X5 と X6 は、エージェントの将来の拡張（P-1・P-2）に当たる。契約（4 章）を先に決めておけば、画面とゲートウェイはエージェントと並行して作れる
